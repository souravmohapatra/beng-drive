# Resumable upload boundary (T09)

The guest listener alone serves `/uploads/:token` and `/uploads/:token/:id`. OPTIONS advertises tus 1.0 capabilities without collection data. Every other operation uses the existing guest session and current collection grant; writes also require the configured public Origin and the session CSRF token. IDs are generated as 128-bit random hex and never derive from a filename. Upload bytes go straight to the bounded NAS worker and are never staged on the app disk.

Pinned `@tus/server` 2.4.5 supplies OPTIONS, POST, HEAD, PATCH and DELETE through its supported datastore methods. An outer guest route enforces exact path/method/body/metadata restrictions and T06 authorization before handing a request to the official server. The request-local `AsyncLocalStorage` context carries the grant, generated ID, pending worker settlements and request ID into the worker-backed datastore; no mutable current-request singleton is used. `create`, `getUpload`, `write` and `remove` call only the bounded worker for payload/sidecar I/O. The stock FileStore never touches product storage. Supported extensions are creation and termination; deferred length, concatenation and creation-with-upload are rejected. The configured URL generator returns only relative `Location` values and never derives an origin from Host or forwarding headers.

For an authorized same-ID PATCH, `getUpload` retains the worker's committed offset in that request context while the ID lock is held. If the official PATCH handler raises its `INVALID_OFFSET` conflict, the error hook returns 409 with that `Upload-Offset`, Tus-Resumable, no-store and the redacted request ID envelope. The hook performs no new storage I/O. Unrelated conflicts and requests without ownership never disclose an offset.

POST admission keeps an exclusive process-local storage claim while probing free bytes, inspecting authoritative sidecar offsets and reserving collection allowance. No PATCH, deletion or recovery mutation may overlap that snapshot. Admission subtracts outstanding unwritten bytes (`declared_size - offset`), the proposed declaration and the free-space floor; missing `creating` artifacts count as offset zero and uncertain artifacts fail closed. The SQLite reservation transaction rechecks grant, allowance and file count; no transaction spans NAS I/O.

PATCH streams may overlap: at most two per session and ten process-wide, with same-ID exclusion and the existing bounded worker pool. Each PATCH captures outstanding chunk reservations and a cumulative granted-byte counter before probing free space. After the probe it subtracts captured reservations, grants made while the probe was running, and this chunk's maximum bytes. Checking and recording the new reservation have no intervening await. This conservatively counts bytes that a free-space sample may already include, but never spends the same margin twice after external consumption. The counter resets only when no PATCH claims remain. Claims and reservations survive response errors/timeouts until actual worker settlement and activity/finalization reconciliation.

Unfinished HEAD shares the bounded transfer group with PATCH, but still holds same-ID exclusion because inspection may truncate an uncommitted tail. Admission, DELETE and separately scheduled recovery/cleanup require an exclusive claim and may return 503/Retry-After while streams run. Readiness/private health report this admission boundary as busy; liveness remains responsive. Concurrent PATCH support does not imply measured public/NAS throughput. External writes after any probe can still reduce free space; worker ENOSPC cannot return an acknowledged offset.

Creation reserves a `creating` row before asking the worker to make a partial and sidecar. A confirmed create moves it to `uploading`, or to `finalizing` for a zero-byte file. A failed or timed-out create keeps its reservation. Reconciliation uses the exact generated ID and expected size/metadata, and never infers success from an arbitrary file of the same size. A request timeout does not release its per-ID lock while the worker may still be active. If the response is lost, a new POST may reserve a different ID; the original remains accounted for until an authorized exact-ID deletion or later cleanup. T10 now [finalizes and recovers completed files](completion.md) after the upload reaches full length; the client waits for the completed receipt before claiming the file was saved.

An authorized DELETE moves a creating or uploading row to `deleting`, removes only that ID's partial and sidecar, verifies absence, then marks it `cancelled`. An empty orphan payload left by an interrupted create can be removed only if its exact generated path is a regular, single-link, mode-0600 zero-byte file. Other uncertain partial states fail closed and retain the reservation. A timed-out storage process keeps the per-ID lock until actual worker settlement; T11 may later coordinate longer-lived cleanup. Original filename metadata allows up to 255 UTF-8 bytes, MIME metadata up to 128; both are stored in the sidecar and returned by HEAD. The storage path uses only the 32-hex-character server ID, giving a safe basename shorter than 160 bytes.

The storage pool waits for child `close` before classifying a missing IPC result as `WORKER_EXIT`. An `exit` event can precede delivery of a result already sent by the worker; waking on `exit` caused intermittent false probe failures during isolated hard-NFS recovery. This does not extend a request deadline or release a timed-out worker's slot early. The fault fixture records each queued operation's outcome and elapsed time before assertions, then verifies drained slots/locks, a fresh probe/readiness, and the committed hash after watchdog restoration.

## Browser transfer flow

The production guest screen uses real session, receipt and tus endpoints. It admits queued files sequentially before starting transfers, avoiding contention between its own POST snapshot and PATCH streams. At most two files transfer together, using 10 MiB chunks and bounded retries at 0, 2, 5 and 10 seconds. Exhausted retries leave an interrupted row with an explicit resume action.

Transmitted bytes, committed offsets and completed receipts are distinct. Only a server `completed` receipt means saved; receiving the final chunk is still finalizing. Receipt polls merge rows by generated upload ID, never filename, including when a poll discovers a creation before its POST response arrives.

Resume URLs and keys are not placed in browser storage. After reload, receipts recover the session/collection's upload IDs; resuming requires reselecting a file and checking its name, size and last-modified metadata against HEAD, followed by explicit confirmation. These checks are not a content hash. Keep the tab open and mobile device awake.

Cancellation retains the reservation until server-confirmed deletion. A failed or deferred cancellation remains `Cancelling` and offers **Retry cancellation**, including after reload; the action is disabled only while its request is pending. Rotation, revocation or expiry clears inaccessible session state rather than exposing another session's receipts.
