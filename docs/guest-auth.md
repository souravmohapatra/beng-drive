# Guest authentication contract (T06)

`POST /api/c/:token/unlock` accepts only an exact `PUBLIC_ORIGIN` Origin and a JSON body containing `key` and `displayName`. The trimmed display name must be nonempty, at most 80 UTF-8 bytes and free of controls. A successful response returns the collection summary, a stable browser-session CSRF token and one `__Host-beng_session` cookie (`Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, no `Domain`). Failed unlocks expose no collection details or cookie. The invitation shell contains no collection data.

The cookie value is a random 256-bit token. SQLite keeps its SHA-256 hash, never the token. Each browser session can hold a separate grant for each collection. A fresh browser using the same key and name gets a different grant and cannot read the first browser's receipts. Re-unlocking an existing grant with the current key keeps its grant ID and original display name; the new display name is ignored. Rotation invalidates old-version grants immediately. A current-key re-unlock refreshes that grant. Revocation and expiry block unlock and reads. Extending collection expiry does not revive an expired grant until current-key re-unlock. Session expiry can extend to cover the latest collection grant, while every request checks its own collection and grant expiry/version.

`GET /api/c/:token/session` returns the current grant's summary, name and CSRF token. `GET /api/c/:token/uploads` returns only that grant's receipts, ordered by creation time and ID descending, up to 100 per page using an opaque cursor. `GET /api/c/:token/uploads/:id` returns 404 for unknown or foreign IDs. These are metadata only; no payload read route exists. All API responses are `no-store`. The owner API remains on the private Unix socket and is absent from the guest listener.

The shared `authorizeGuest` guard checks the current collection, hashed cookie session, collection-specific grant version and expiry, and optional upload ownership on every call. For future authenticated writes it also checks exact `PUBLIC_ORIGIN` and the session-bound `X-CSRF-Token`. T09 still must integrate this guard with actual tus create, HEAD, PATCH and DELETE operations; T06 alone does not make upload routes available.

Limiter state is local SQLite migration 3. Inside a `BEGIN IMMEDIATE` transaction it prunes expired attempts and source buckets, checks the rolling windows, records each admitted unlock outcome, and creates/refreshes grants only after the full body has been read. The fifth failed attempt per source IP and collection gets its normal error; the next request is 429. A collection's 100th attempt, including successes and malformed bodies, gets its normal outcome; the next is 429. The 1000th global attempt in 60 seconds gets its normal outcome; the next is 429. Rejected attempts do not move any window. `Retry-After` is rounded up to 1–900 seconds and matches `error.retryAfterSeconds`. At 10000 live distinct source IP/collection buckets, a new pair is denied until an old entry ages out. Expired auth sessions and grants are retained to preserve receipt foreign keys; no payload or receipt cleanup is performed here.

The source IP is the normalized connection address only. `Host`, `CF-Connecting-IP`, `Forwarded` and `X-Forwarded-For` are ignored. This makes the existing loopback connector share a conservative source bucket. Trusting a forwarded client IP requires a separately verified and isolated proxy path under T04; no such mode is enabled. T04's public/private route and Access gates remain open, and the guest routes have not been published to the Internet.
